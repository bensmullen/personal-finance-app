# Level 3 pilot screen-state and interaction acceptance matrix

**Status:** proposed task/UI interaction target for H04 Barlow (novice) and H08 Ortega (retirement/care), to be reviewed in the first Level 4 design round. Read with [33 task traces](level3-interaction-traces.md), [observed visual baseline and navigation contract](level3-visual-baseline-navigation.md), [six-stage journey](user-journey-level3.md), and PFA-UX-015–023. This specifies *required information, user decisions, behavior, navigation and recovery*; it does **not** prescribe exact styling, pixel placement, schema/entity names in the UI, or claim any target behavior already works.

## 1. Screen-state design rules — shared

A screen is never just "loaded" or "error." Each materially relevant task has states **empty/new, known/current, draft/dirty, working/processing, partial/incomplete, conflict/invalid, unsupported, stale, save failed and restored** as applicable. Do not implement unused states on unrelated screens, but do not drop a reachable failure branch.

**Visibility:**
- Initial screenful: current household and task, known data/as-of scope, single main question and action. If blocked, show one *concise, named* actionable cause; other related errors must not push unrelated financial content several screenfuls down. The [first successful UX capture #38971983269](https://github.com/bensmullen/personal-finance-app/actions/runs/38971983269) demonstrates the opposite problem across all six captured views.
- One scoped disclosure for source/assumptions, one for optional advanced domain details, and a distinct opt-in technical trace; never hide essential caveats or blocking save errors behind collapse.
- All significant values name owner/person, time basis, unit, actual/assumed/derived status and source when material.
- At 390px, current section must be visible in the nav and one clear back/return control must not require navigating a horizontally clipped submenu; focusable headings/inputs; no hover-only instruction.
- No duplicate editors: when a target row says "Edit", open the canonical writer identified by the 62-family fact registry. On save, return to **origin screen + task context**: plan, person, selected period, and field/metric. Cancel/failed save must leave the former financial fact intact.

## 4. Critical microinteraction states for prototype authors

| Element and entry | User controls / feedback | Focus, cancel, failure and status |
| --- | --- | --- |
| Task card in S01 | One named question and one action; optional secondary explanation | On choice route to S02/S06/S07/S09, retaining identity and as-of; unsupported question displays exact caveat without navigating into empty schema form |
| Owner-edit sheet S16 | Named account/person + source/date; common fields; expandable advanced; Save/Cancel | Focus first missing/invalid field. Cancel/Esc restores origin scroll and filter; validation maps to field and single summary; no duplicate authority |
| Field help | Concise "What is this?" + unit/frequency, example and effect | Works on focus/touch/keyboard; non-modal help doesn't require mouse hover; never substitutes help text for a required input |
| Conflict review | Two named source values, scope (person/employer/date/year), allowable source-selection or defer | Defer preserves both; disabled unsupported edit provides correct import path; never "newer is correct" by default |
| Plan age selector | Person selector, end age input, calendar end date, Edit/Reset to 90; retirement age S10 separate | Existing saved plan takes precedence; validation of already past age, missing DOB and 40+ year support; changing age shows exact affected result freshness |
| Forecast status | Current/Running/Partial/Unsupported/Stale/Failed and abbreviated cause | Never display long per-year tax diagnostics on every unrelated page; status explanation and source recovery expand only on demand; old result retains old basis |
| Plan alternative | Baseline and variant name, changed assumptions, unsaved/persisted marker, comparison basis | Missing #105 prevents Save As as if implemented; failed duplicate preserves baseline; unmatched basis blocks numerical delta |
| Save identity | Saved model vs unsaved draft vs exported plaintext backup | Confirm actual destination only on success; failure doesn't claim durable save; public/demo origin not trusted for personal model |
| Mobile subnav | Current section always visible, stable back and heading; one-column summary and focused editor | Avoid clipped active label / horizontal hidden route; each page has same clear way back and accessible focus |
| Destructive choice | Label which model/demo/source/plan will be affected, Cancel/Confirm | Cancel returns to exact context; errors retain former verified data; no accidental real-data deletion through example reset |

## 5. High-value end-to-end pilot acceptance and deliberate failures

**H04 uncoached script:** From fresh demo choose H04 → explain how much cash is left after ordinary spending and required debt → inspect card interest/obligation → find investments empty state → examine a *proposed* first workplace contribution and source-payroll constraints → see age-90/65 planning setup (45-year horizon) → identify whether full after-tax forecast is supported → compare (if #105) debt versus spending versus contribution choice → save and resume without re-entering unchanged facts. Force: synthetic fixture unavailable, unknown withholding, unknown employer plan term, old result after modification, long-horizon calculation unsupported, save failure.

**H08 uncoached script:** Choose H08 → verify whose money is included → inspect pension/retirement account separation → edit each spouse's retirement age differently → inspect Avery support expenses and separately held resources → review dependent-care tail after later spouse's age-90 date → run supported forecast and identify healthcare/benefit gaps → compare 62/67 choice only with matching basis → preserve baseline and resume. Force: ambiguous adult dependent ownership, conflicting dated health coverage, unsupported public benefit, horizon extension beyond runtime capability, plan duplication unavailable.

**Acceptance gating:** each task has a named start, one successful completion condition, an explicit Cancel/Back path, an error path that retains verified state, and a source/capability boundary. All H04/H08 critical task states shall be demonstrated at 1440px and 390px in an approved Level 4 target and then in PM uncoached UAT; do not claim screenshot-only approval or implementation complete.

**Dependencies:** Current one-click demo ≠ eight-persona fixtures (#108). Existing What If screen ≠ independent saved-plan comparison (#105). Existing 1–40 year authoring limit ≠ supported age-90 execution. Unsupported tax/care/legal consequences are not solved by the UX prototypes. Stage-gated backend and task-issue work follows design approval and must preserve accepted financial semantics.
